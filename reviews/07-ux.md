# UX Review — Onboarding, Empty States, Errors, End-to-End Coach & Parent Paths

*Reviewer stance: a non-technical parent with two kids in the club, standing in a parking lot on one bar of signal, trying to pay a registration fee before it closes at midnight. Doesn't care why something failed — cares whether the screen tells them what to do next. Every finding below is something that would plausibly end in a text to the club director.*

Scope covered: mobile onboarding (`app/(auth)/*`), web coach setup wizard (`web/app/onboarding`), web parent flows (`web/app/join`, `web/app/register/[token]`, `web/app/pay/*`, `web/app/portal`, `web/app/offer-response`, `web/app/guest-invite`), the four mobile tabs and their empty states, the coach admin panel, chat/messaging, and the RSVP and fee-payment paths end to end.

**Cross-reference note:** this branch has sibling reviews already covering adjacent ground. Rather than re-litigate the same bug twice, findings already fully documented elsewhere are cross-referenced with one line instead of repeated: the parent-facing RSVP silent-failure bug (`schedule.tsx`/`event/[eventId].tsx`) is `05-mobile.md`'s top Critical finding; gallery/announcement delete swallowing errors are `08-quickwins.md` #5–6; the `/join` blank-Suspense render is `06-web.md` #3; webhook/reconciliation and cron-status payment findings are throughout `02-payments.md`. None of those are repeated in full below.

## 1. Coach onboarding — web setup wizard (`web/app/onboarding/page.tsx`)

This is the single most important surface in the product per CLAUDE.md's "zero involvement from Rick" self-serve promise, so it gets the most scrutiny.

Severity: Critical
Location: web/app/onboarding/page.tsx:337-358 (`AuthStep.submit`)
Problem: No try/catch around `supabase.auth.signUp`/`signInWithPassword` on the very first screen of the wizard — a thrown/network error on a flaky connection leaves `loading` stuck `true` forever, button permanently reads "Please wait…" with no way out but reloading and re-typing everything.
Fix: Wrap the body in try/catch, `setLoading(false)` in a `finally`, generic fallback message on catch — matching the pattern already used two steps later in `ClubStep.submit`.
Effort: 15-30 minutes

Severity: Critical
Location: web/app/onboarding/page.tsx:1113-1204 (`confirm`)
Problem: Retrying "Confirm & go live" after a partial failure (verified: line 1201's own error message admits some rows failed) re-inserts every team/player/event that already succeeded on the *previous* attempt — the insert loops at 1116, 1135, 1172 run unconditionally over the full local arrays with no "already saved" id tracking, unlike the AI-import merge path (`mergeParsedData`, 944-1068) which deliberately dedupes. A coach who hits "try again" after a one-row failure duplicates their whole roster and schedule.
Fix: Track a `dbId` per row once inserted; on a repeat `confirm()` call, skip rows that already have one.
Effort: 2-4 hours

Severity: Critical
Location: web/app/onboarding/page.tsx:897, 1116, 1757-1760, 1834-1838, 2162-2166
Problem: Nothing stops "Confirm & go live" from succeeding with zero teams. A skipped/failed AI import seeds one blank-name team that the Review screen's own filter (897) then hides, so a rushed coach can click Confirm on an apparently-normal Review screen and land on a Done page that says "Your teams, roster, and schedule are all set up" directly above "0 teams · 0 players · 0 events."
Fix: `if (!teamOpts.length) { setError('Add at least one team before going live.'); return; }` in `confirm()`, and soften the Done copy when counts are 0.
Effort: 30-60 minutes

Severity: High
Location: web/app/onboarding/page.tsx:430-440, 1964-1969, 2195-2200; web/app/api/onboarding/route.ts:19-20,50-51
Problem: Clicking Back from Upload to Club re-mounts `ClubStep` with blank state — the already-created `clubName`/`slug`/`color`/`logo` are never passed back in. Re-entering the same info 409s with "That URL slug is already taken," which is confusingly *their own* club from seconds earlier. A full page refresh handles this correctly via `resume()` (2000-2049); the wizard's own Back button is worse than reloading the page.
Fix: Lift `name`/`slug`/`primary`/`logoPreview` into the parent and pass as `ClubStep` initial values, or skip the Club step entirely on Back once `clubId` is set.
Effort: 1-2 hours

Severity: High
Location: web/app/onboarding/page.tsx:350, 496; web/app/api/onboarding/route.ts:53; web/lib/apiAuth.ts:19,29,43
Problem: Several paths show raw backend text: `profErr.message` (a Postgres/RLS error) straight into the UI at 350; `ClubStep` shows the raw create-club error at 496 for anything that isn't the one handled slug-conflict case; and an expired session mid-wizard returns the literal string `"Unauthorized"`/`"Forbidden"` with no explanation.
Fix: Allowlist known-friendly Supabase Auth messages client-side, generic fallback otherwise; special-case 401/403 as "Your session expired — refresh and log in again."
Effort: 30-45 minutes

Severity: Medium
Location: web/app/onboarding/page.tsx:614-623 (`UploadStep.addFiles`)
Problem: No try/catch around `toParseAllPayload(f)` in the file loop — one corrupted/unreadable dropped file throws before `setConverting(false)` runs, so the drop zone's button is stuck reading "Reading files…" forever with no error and no indication which file was bad.
Fix: try/catch per file inside the loop, `finally { setConverting(false) }`, report which file(s) failed.
Effort: 20-30 minutes

Severity: Medium
Location: web/app/onboarding/page.tsx:2129-2135; web/lib/parseAllClient.ts:91,122-124
Problem: When the AI import pipeline fails outright, the real, already-written, actionable message ("...the import seems to have stalled. Please try again or add files manually.") is computed one layer down but discarded — the coach always sees the hardcoded generic `'Import failed'`.
Fix: Use `outcome.error` as the displayed text instead of the literal string.
Effort: 15 minutes

Severity: Medium
Location: web/app/onboarding/page.tsx:1591-1602, 2051-2059
Problem: The outer Back button stays active while `ReviewStep` is saving (only guarded for `step === 'processing'`, not the review-save state) — clicking it navigates to Upload while `confirm()` keeps running; if it later succeeds it calls `setStep('done')`, silently teleporting the coach to the Done screen after they thought they'd left.
Fix: Disable/hide Back while a save is in flight (lift the `saving` flag to the parent or no-op `goBack()` during it).
Effort: 30-45 minutes

Severity: Low
Location: web/app/onboarding/page.tsx:1263, 1289, 1470, 1481
Problem: Player/event rows on the Review screen are fixed-width CSS grids (`min-w-[620px]`/`min-w-[1000px]`) requiring horizontal scroll on a phone to reach the team-assignment dropdown or the delete button — on the single densest, most-edited screen in the whole wizard, for a wizard explicitly meant to be run from a phone.
Fix: Stack fields into a card layout below a breakpoint instead of a fixed-width grid, at least for name/team/delete.
Effort: 4-8 hours

Severity: Low
Location: web/app/onboarding/page.tsx:541-553
Problem: Club name/slug fields have no visual "required" cue (no asterisk, no `required` attribute) unlike `AuthStep`'s fields — the only sign is the error after clicking Continue.
Fix: Add `required` + asterisk for consistency.
Effort: 10 minutes

## 2. Parent & coach signup — mobile app (`app/(auth)/*`)

Severity: Critical
Location: app/(auth)/create-team.tsx:53-73 (`handleCreate`)
Problem: A coach setting up their own team in-app runs 5 sequential, un-timeout-guarded writes (role→org_admin, insert club, set profile.club_id, insert team, insert team_members), each surfacing a raw backend string on failure (`` `Failed to create club: ${clubErr?.message}` ``, etc.). Unlike login/register/reset-password, this screen has none of the codebase's now-standard 6s timeout-race pattern. If step 3+ fails on a flaky connection, the coach is left with an orphaned club record and a scary raw error, and tapping the button again (there's nothing marking the club as already created) creates a *second* club under a different random slug.
Fix: Apply the same `withTimeout` pattern used in `login.tsx`/`register.tsx`; make the sequence idempotent/resumable (e.g. check for an existing club owned by this user before inserting a new one on retry); replace raw `.message` interpolation with friendly copy.
Effort: 1-2 hours

Severity: High
Location: app/(auth)/find-team.tsx:56-77 (`handleFindClub`), input at 118-123
Problem: The only lookup is an exact, case-normalized match on `clubs.slug` — no fallback search by club name. A parent who only knows their club's name (the CLAUDE.md "Journey 3 — organic discovery" persona) types it in, gets "No club found with that slug," with no explanation of what a slug even is or where to find one.
Fix: Fall back to an `ilike` search on `clubs.name` when the exact slug match misses, and/or add one line of copy explaining "ask your coach for your club's Pulse FC link or code."
Effort: 30-45 minutes

Severity: Medium
Location: app/(auth)/_layout.tsx (whole file) and app/(app)/[clubSlug]/support.tsx
Problem: The in-app "Contact Support" screen only exists at a `[clubSlug]`-scoped route, so it's unreachable to exactly the population most likely to need it: anyone still stuck in onboarding (e.g. the find-team dead end above). find-team.tsx's only escape hatches are "Sign out" and a link out to the coach-only web onboarding URL.
Fix: Add a lightweight, club-independent "Need help?" link (mailto or a stripped-down version of support.tsx) somewhere in the `(auth)` stack, at minimum on find-team.tsx.
Effort: 30-45 minutes

Severity: Medium-High
Location: app/(auth)/profile-setup.tsx:151-162 (`handleSendGuardian`)
Problem: A left-in diagnostic check shows `Alert.alert('Session out of sync', \`App had ${user.id.slice(0,8)}… but the server session is ${liveUser?.id?.slice(0,8) ?? 'none'}…. Please sign out and back in, then try again.\`)` — truncated UUIDs and "session" jargon shown verbatim to a parent trying to invite a co-parent during onboarding.
Fix: `Alert.alert("Couldn't send invite", "Please sign out and back in, then try again.")`; keep the UUID comparison in a `console.warn` only (as the surrounding comment already does).
Effort: 10 minutes

Severity: Medium
Location: app/(auth)/register.tsx:100-134 (`handleGoogle`/`handleApple`)
Problem: `login.tsx` has a documented, deliberate self-heal (`recoverOrShowError`, lines 121-128) for exactly this case: an SSO call that times out on flaky signal but actually succeeded server-side. `register.tsx`'s equivalent handlers were never given the same treatment — they go straight to `setError(e.message)` — so a parent/coach *signing up* (not logging in) via Google/Apple on bad signal can see a false failure error even though their account now exists, and may retry into a confusing "already registered" state.
Fix: Reuse `recoverOrShowError` (or extract it to a shared helper both screens import) in `register.tsx`'s `handleGoogle`/`handleApple`.
Effort: 20 minutes

Severity: Medium
Location: components/ui/ErrorBanner.tsx:9-15
Problem: Every inline error across the auth flow (login, register, create-team, find-team, reset-password, profile-setup) auto-fades to invisible after 4 seconds with no way to recall it — the container stays in the layout (leaving an empty gap) but the message itself is gone. Combined with the raw/technical messages found above, a confusing string now has an even smaller window to be read before it vanishes with no trace.
Fix: Don't auto-dismiss errors that require action (keep the 4s fade for pure success/info toasts only, if any); at minimum extend the timeout and let a re-tap of the failed action re-trigger the fade-in rather than relying on the first, possibly-missed, 4-second window.
Effort: 20-30 minutes

## 3. Parent web flows — invite, registration, and payment pages

These are the pages a parent reaches by tapping a link in a text/email, generally not logged into anything, exactly the "one bar of signal, midnight deadline" scenario this review is framed around.

Severity: Critical
Location: web/app/pay/portal/page.tsx:46-62 (`loadFees`), empty state at 189-195
Problem: Both Supabase queries in `loadFees` discard `error` — any query failure (RLS hiccup, transient network drop) renders the exact same UI as genuinely owing nothing: "✅ All clear! No fees found for your players." A parent whose fee list simply failed to load is told, in the money page, that they have nothing to pay.
Fix: Capture `error` on both queries; on failure show a distinct "We couldn't load your fees — try again" state with a retry button, never fall through to the empty-state copy.
Effort: 30 minutes

Severity: Critical
Location: web/app/pay/[token]/page.tsx:62-82 (`finishPayment`)
Problem: Verified directly — the function only branches on `confirmErr` (shown as error) and `paymentIntent?.status === 'succeeded'` (shown as success). Every other terminal status falls into a bare `else { setProcessing(false) }` with zero UI feedback. `status === 'processing'` is the *normal, expected* outcome for the ACH/bank-account rail — the default option, badged "LOWER FEE" (line 550-553) — so a parent who pays by bank transfer has the Pay button silently re-enable to what looks like an untouched form, with no idea whether their bank payment is pending, failed, or lost, right after handing over real banking details.
Fix: Add an explicit branch for `processing` (and any other non-terminal-error status) that shows "Payment submitted — your bank payment is processing and usually clears in 1-2 business days, you'll get a receipt by email" instead of silently resetting to the idle-looking form.
Effort: 1-2 hours

Severity: Critical
Location: web/app/join/page.tsx:108-133 (`handleSignup`)
Problem: No try/catch around the `fetch('/api/accept-invite', …)` call. On a dropped connection — the exact scenario this page exists for — the fetch rejects, execution halts, and `submitting` (set `true` at 114) never resets: "Creating account…" spins forever with no retry short of reloading and losing the typed password.
Fix: Wrap in try/catch/finally; on catch, "Network error — check your connection and try again," always reset `submitting`.
Effort: 15 minutes

Severity: Critical
Location: web/app/register/[token]/page.tsx:154-252 (`handleSubmit`)
Problem: No try/catch wraps this handler. The registration is already durably committed by the RPC at line 209 *before* the confirmation-email fetch at 233 runs — if that (or an earlier file upload) throws on a flaky connection, `setDone(true)` at 251 never fires. The parent sees an infinite "Submitting…" spinner despite a registration that may carry a real payment obligation already existing, and will likely resubmit (creating a duplicate) or give up and text the club.
Fix: Wrap in try/catch/finally so `setDone(true)` always fires once the RPC has returned successfully; make the confirmation-email call fire-and-forget so its own failure can't block reaching the success screen.
Effort: 30 minutes

Severity: Critical
Location: web/app/offer-response/page.tsx:47-60
Problem: The mount-time `fetch('/api/tryout/process-response?token=…')` has no `.catch()`. A failure leaves `loading` `true` forever — the very first thing a parent sees on this tryout-offer link is a permanent "Loading your offer…" with no retry.
Fix: `.catch(() => { setData({ error: 'Could not load this offer. Check your connection and try again.' }); setLoading(false); })`.
Effort: 10 minutes

Severity: Critical
Location: web/app/guest-invite/[guestId]/page.tsx:74-80, 100-114
Problem: Same pattern twice: the initial fetch has no `.catch()` (permanent "Loading invitation…" on a network blip), and `handleAction` has no try/catch/finally at all — if the accept/decline POST fails, `setPending(null)` never runs and the tapped button (Confirming…/Declining…) stays stuck indefinitely.
Fix: Add `.catch()` to the load; wrap `handleAction` in try/finally so `setPending(null)` always runs, and surface `!result.ok` as an inline error instead of silently doing nothing (see High finding below).
Effort: 20 minutes

Severity: High
Location: web/app/pay/portal/page.tsx:126-165
Problem: The only entry point to "My Fees" is a password login with no "Forgot password?" link and no signup path, even though a working reset-password page exists elsewhere in the app and nothing on this page calls `resetPasswordForEmail`. A parent who followed a payment link but doesn't remember a password has zero self-service recovery on the one page where money is on the line.
Fix: Add a "Forgot password?" link calling `supabase.auth.resetPasswordForEmail(email)` and routing to `/reset-password`.
Effort: 1-2 hours

Severity: High
Location: web/app/guest-invite/[guestId]/page.tsx:100-114
Problem: When the accept/decline POST returns `ok: false`, nothing is surfaced — the buttons just re-enable with no message, so a real failure (server error, expired invite) looks identical to nothing having happened.
Fix: `if (!result.ok) setError(result.error ?? 'Could not save your response — please try again.');` rendered near the buttons.
Effort: 20 minutes

Severity: High
Location: web/app/pay/[token]/page.tsx:474-491, 578
Problem: Typing a partial-payment amount above the balance (or ≤0) silently disables the Pay button with no message — on a payment form, an inert button with no explanation reads as broken, not "fix your input."
Fix: Render an inline "Enter an amount up to {balance}" whenever the parsed amount is invalid.
Effort: 20 minutes

Severity: Medium

Problem: Every `signInErr` — wrong password or a network/timeout failure — is shown as `'Incorrect email or password. Please try again.'`. A parent with the right password but bad signal is told their password is wrong.

Severity: Medium

## 4. Fee-payment notifications don't lead anywhere in the app

Severity: High
Location: app/(app)/[clubSlug]/notifications.tsx:283-296
Problem: Tapping a "❌ Payment failed," "fee_reminder," "payment_confirmed," or "payment_received" notification does nothing beyond marking it read — the comment at 283 says so explicitly ("no dedicated mobile screen ... nothing further to navigate to"). This isn't a missing-data problem: every one of these notification types already carries `player_fee_id` in its `data` payload (confirmed in `web/app/api/stripe/webhook/route.ts:161-178`, `send-fee-reminder/route.ts`, `send-fee-notification/route.ts`, `cron/apply-late-fees/route.ts`). A parent whose card gets declined gets a push telling them exactly that, and tapping it to go fix it does nothing — they have to independently remember the Home tab shows an outstanding-fees card and navigate there themselves.
Fix: Look up the fee's `payment_token` from `player_fee_id` and open the same pay flow the Home tab's `payNow()` uses (`WebBrowser.openBrowserAsync`), or navigate to Home and open the fee modal pre-filtered to that fee.
Effort: 1-2 hours

## 6. Coach admin panel — roster, invites, events, broadcasts, AI import

Severity: Critical
Location: app/(app)/[clubSlug]/create-event.tsx:588-625 (`handleSave`)
Problem: `handleSave` never checks the `error` returned by any `supabase.from('events').insert(...)` call — on failure (network blip, RLS, constraint violation) the coach still sees `setSaving(false); router.back();` as if the event was created. For the recurring-events loop (596-610) a partial failure is silently swallowed the same way.
Fix: Check `error` on every insert; on failure, re-enable Save and show a specific alert; for the recurring loop, report which occurrences failed rather than continuing silently.
Effort: 30-45 minutes

Severity: Critical
Location: app/(app)/[clubSlug]/create-event.tsx:627; entry point app/(app)/[clubSlug]/admin/index.tsx:503-512
Problem: `canSave` only checks `title.trim()` and `!saving`, never that a team exists. On a brand-new club with zero teams, "Create Event" is offered as one of three onboarding options on the admin empty-state screen, where `useTeam()` genuinely returns `team: null`. Tapping Save there silently hits `if (!title.trim() || !team) return;` before anything else runs — the button looks enabled and tappable, and nothing happens: no spinner, no alert, no navigation.

Severity: Critical

## 8. A root cause behind several of the above: the app can't detect "connected but broken"

Severity: High
Location: hooks/useNetworkStatus.ts:9; components/ui/OfflineBanner.tsx; app/(app)/[clubSlug]/(tabs)/_layout.tsx:169
Problem: `isConnected` is derived from NetInfo's `state.isConnected !== false` — a radio-level check ("is the device attached to a network interface"), not `state.isInternetReachable` (an actual reachability probe). On one bar of signal — this review's own framing — a phone reads as fully "connected" while requests time out or fail, so `OfflineBanner` never appears in precisely the scenario it exists for. Every silent-failure finding above (RSVP writes, chat setup, email sends, Home tab data) happens on a connection this banner considers fine.
Fix: Switch the check to `state.isInternetReachable === false` (NetInfo supports this on both platforms), or treat `isInternetReachable === null` (unknown/still probing) conservatively rather than defaulting to connected. Consider also rendering the banner outside the `(tabs)` layout so screens like event detail and settings get the same signal.
Effort: 30-45 minutes

## What's already done well

- **Auth cold-start hardening is genuinely excellent.** `hooks/useAuth.tsx`'s timeout-raced session restore, `AsyncStorage` profile cache for instant return-visit rendering, and `lib/authRouting.ts` reusing the same pattern for post-login routing are exactly the right shape for a flaky-connection persona — this is infrastructure other flows in the app (`create-team.tsx`, `create-event.tsx`'s save path) should be extended to, not a gap in itself.
- **Empty states are consistently thoughtful, not boilerplate.** Roster, Schedule, Chat, and Notifications all distinguish "nothing here yet" from "you're all caught up," and use role-aware copy ("Add your first player" for a coach vs. "Your coach hasn't added the roster yet" for a parent) rather than one generic string reused everywhere.
- **`ClubSuspendedModal`** is a genuinely well-designed blocking state: role-aware copy (org_admin gets a support email CTA, coach/parent are told to contact their own club instead of Pulse FC), no accidental dismiss, clear next step either way.
- **The web onboarding wizard's AI-import review screen** (`ConfBadge`, per-row retry with dedup, the "Unassigned" catch-all section, upfront email validation before any DB write) is a strong example of turning an AI black box into something a non-technical coach can actually audit and trust before committing.
- **`web/app/pay/[token]/page.tsx`'s card-surcharge disclosure flow** — validate the card, show the real card-specific fee, require an explicit confirm-or-go-back before charging — is careful, transparent design on the one page where trust matters most.
- **Partial-failure reporting done right, when it's done at all:** `pending-invites.tsx`'s `handleResendAll` ("Sent X of Y" plus the literal list of failed emails) and `register/[token]/page.tsx`'s race-lost-spot-to-waitlist handling are the pattern the broadcast/roster-import/admin-dashboard findings above should be following — the codebase clearly knows how to do this well, it's just inconsistently applied.
- **`app/(auth)/reset-password.tsx` and `web/app/reset-password/page.tsx`** both correctly treat `updateUser({ password })` as idempotent and tell the user so on a timeout ("if it already went through, updating again is safe") instead of guessing.
